## 2026-09-19 · 下载慢的真因（不是网速）与解法：探测式抢高速档

- 诊断（全部实测）：
  | 层 | 实测 | 判定 |
  |---|---|---|
  | 本机到 Cloudflare | **5,177 KB/s（41 Mbps）** | 本机不是瓶颈 |
  | 中转站图片 CDN | 同一主机两次请求 **1.26 KB/s ↔ 97.2 KB/s（差 77 倍）**，TTFB 0.8–4.0s | **对端送图极不稳定** |
  | 带 `Range` 请求 | 返回 **200**（非 206） | **不能续传、不能分块并行** |
  | 图生图内联 base64 | `/images/edits` 忽略 `response_format`（代码已实测记录） | **绕不开这条 CDN** |
- 推论：速率抖 77 倍 + 不能续传 ⇒ **用长超时去傻等是最差策略**（一旦掉到低速档就只能等超时，
  然后从头再来）。正解是"**低速就立刻断、重试抢档**"。
- 解法：用 curl 自带的 `--speed-limit <B/s> --speed-time <秒>`（速率持续低于阈值超时即主动中断），
  排一个"先严后松"的门槛计划；下完仍做 `Image.open().load()` 完整解码校验。
- ⚠️ **门槛不能定高（第一版就踩到）**：首版用 `(40K,5)(40K,5)(25K,6)(25K,6)…`，
  **把一次平均 61.6 KB/s 的尝试也杀了**（它中途瞬时掉到 40 KB/s 以下被 curl 断开）。
  这台 CDN 的工作区间实测就是 **20–60 KB/s**，偶尔崩到 1.5 KB/s，所以门槛要按实测区间定，
  不能用"理想带宽"去定；而且**没有续传 ⇒ 门槛越严、白白重下的字节越多**。
  修正后的计划：`(20K,8)(20K,8)(12K,10)(12K,10)(8K,12)` 然后无门槛；门的 max-time 给到 600–900 秒
  （10 MB / 20 KB/s ≈ 500 秒，**必须让它跑完**）。
- 效果（同一个 10 MB / 3840×2160 的文件）：
  **旧策略**：两次 900 秒各只取回约 1.9 MB，均失败 → **30 分钟白费**；
  **新策略**：4 次快速淘汰（110 秒）＋ 第 5 次 12 KB/s 门槛下 **511 秒**完成 → **约 11 分钟下完**。
- 配套工程：`round_lib/fetch_url.py`（按 URL 补下，或 `--pending` 批量补齐）＋
  `round_lib/pending_urls.json`（**生成一拿到 URL 就落盘**，下载失败也不丢）。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 别把"投喂被压坏"当成必然毁结果：提示词本身也承载特征

- 现象：我事先判断 4K 那版"投喂被压成内容二值化＋身份参考 240px 模糊，所以脸会不像、网点会丢"，
  据此劝用户不要等它下载。**结果实测相反**：4K 版的脸没跑掉、荷叶边与裙子的网点也在。
- 根因：我把"投喂损失"当成了唯一信息源。而这一版的提示词里已经**逐条写明了角色特征**
  （脸型／眼型／发型／头饰／服装部件）与**画法**（网点、排线、明度层级），
  信息并不只来自投喂图。
- 教训（双向的，别过头）：**投喂被压坏 ≠ 结果一定坏**，因为提示词承载了一部分；
  但也**不能反过来认为"投喂随便压"**——v7 那轮的"脸不像"正是糊参考导致的，两件事要分开看：
  **当提示词里已经把该特征写清楚时**，投喂压缩的损失可被部分抵消；
  **当特征难以用文字写清时**（长相、笔触），投喂的清晰度就是决定性的。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 输出一上 2K/4K，下载成为新瓶颈；且截断文件"能打开"但不完整

- 现象：1K 输出（约 2 MB）下载一直是几秒的事。这次跑 2K（4.12 MB）与 4K（约 15 MB），
  下载速率掉到 **10–25 KB/s**：4.12 MB 要 3 分钟、4K 要十几分钟。同时暴露三个坑：
  ① **两个大文件同时下会互抢带宽**——实测并行时跌到约 **1 KB/s**，600 秒只取回 658 KB / 4.12 MB；
  ② **`-C -` 断点续传在这台 CDN 上无效**——它不支持 byte range，
     curl 报 `HTTP server does not seem to support byte ranges. Cannot resume.`，只会从头再来；
  ③ **截断的文件 `Image.open()` 不报错**，只有调用 `.load()` 才抛
     `OSError: image file is truncated`。所以"能打开"和"看文件大小"都会漏判
     （实测 2.93 MB / 4.12 MB 的截断文件，`open` 正常、`load` 报错）。
- 有效动作：
  ① 大输出走**后台任务**下载，超时给 300–900 秒（`run_round.py` 的下载默认已从 60 秒改到 300 秒）；
  ② 多个大文件**串行**下，不要并行；
  ③ 下完**必须 `Image.open(p).load()` 做完整解码校验**（已加进 `run_round.py` 的下载函数）；
  ④ 拿不准就先用 `--max-time 15` 探一次速率，再定超时预算。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 高分辨率下"投喂体积"由目标尺寸决定；**横向画幅是省额度的杠杆**

- 现象：想在 4K 下继续用清晰的身份参考，无论把参考源图缩到多小都没用——
  4K 下把参考缩到 **320px**，归一化到 3840×2160 后**仍要 1.51 MiB**。
- 根因：`normalise_to_size` 会把每张投喂图**统一缩放到目标尺寸**再编码，
  所以体积 ≈ f(目标像素总数, 内容熵)，**与源图分辨率基本无关**。
- 有效动作：**降低目标像素总数**。同一档位里**横向画幅的像素数更少**：
  实测（内容+参考合计，已知上限约 1.67 MiB 通过）
  | 画幅 | 像素 | 内容二值+参考240（勉强档） | 内容灰16+参考900（理想档） |
  |---|---|---|---|
  | 4K 方 2880×2880 | 8.29 Mpx | 1.68 MiB | 3.32 MiB ✗ |
  | **4K 横 3840×2160** | 8.29 Mpx | **1.54 MiB** | 3.02 MiB ✗ |
  | 2K 方 2048×2048 | 4.19 Mpx | 1.05 MiB | 2.16 MiB ✗ |
  | **2K 横 2048×1152** | 2.36 Mpx | 0.66 MiB | **1.38 MiB ✓** |
  结论：**要"高分辨率 + 身份参考不失真"，只有 2K 横向这一档能两全**；
  真 4K 必须接受"内容二值化（网点丢失）＋参考压到 240px 模糊量化（脸会不像）"。
  另外：横向目标会**居中裁切**投喂图，所以**投喂图要自己先裁成目标比例**，
  否则接口的居中裁切会把眼镜/脸切掉（本例把内容与参考都预先裁成 16:9）。
- 可复用？：是 → 已写入本节 + `pipeline-notes.md`

## 2026-09-19 · "画面太深/太淡"这类质感要求：先量化成剖面，再并行多版择优

- 现象：同一次三版对比里，用户说"B 的动作神态都对，但画风太深，不如 C 的淡然"。
  而 A/B/C 三版的提示词**只差中间那格的表情一句**——**深浅差根本不是写出来的，是模型方差**。
- 根因（可复用）：质感类要求（深／淡、脏／干净、厚／薄）在提示词里**本来就没有对应指令**，
  所以它天然带大方差；反复调措辞等于在跟噪声搏斗。
- 有效动作（三步）：
  1. **先把质感量化成剖面**：纸白占比、墨量（亮度<0.35 占比）、灰调（0.35–0.80 占比）、
     亮部、平均亮度、对比跨度。实测 B→C 的剖面对照：纸白 0.604→0.670、灰调 0.232→0.179、
     墨量 0.061→0.040、平均亮度 0.842→0.881、对比跨度 0.698→0.590。
     **"淡"就是这么被翻译出来的**：纸白更多、中间调网点更少、大块深灰更少、对比更收。
  2. **把剖面写成规则**加进提示词（把"中间调尽量不铺网点、头发排线疏一些、近黑的只有少数几处"
     写死），并设一条**不被调淡冲掉的下限**（本例是"黑领结与瞳孔仍要近黑"）。
     工具：`round_lib/tone_report.py`（只读，输入一批图 + `--ref 基准图`，输出剖面表与"与基准的距离"排序）。
  3. **并行多版 + 指标择优**：同一份提示词并行跑 3 版（`--concurrency 3`，实测 3 版 75 秒 vs 串行 225 秒），
     再用 `tone_report.py` 排序挑。**比反复调词省时间，而且选择过程可复现。**
- 附带一条口径提醒：**"与基准的距离"与"是否达到阈值"是两个不同的问题**——
  本例 v13_1 距基准最近（0.074）但只过 4/5 条阈值；v13_3 五条全过却**越过了基准**（比 C 还淡）。
  交付时两个口径都要报，由人来定"要像 C"还是"要更淡"。
- 可复用？：是 → 已写入本节 + `references/pipeline-notes.md`（工具与阈值口径）

## 2026-09-19 · 夸张表情是"眼型被放大"的触发器（第二次出现，已有明确机制）

- 现象：多视图页里，指定"中间那格张嘴大笑"之后，**那一格的脸明显比另外两格幼**——
  眼睛变大变圆、虹膜放大、高光变大、脸颊推圆。同一机制在 v8 那轮已经出现过一次。
  而"左＝半阖眼平静""右＝含笑"两格都正常。
- 根因：**夸张表情会连带改变五官比例**。模型画"张嘴大笑"时会同时把眼睛放大、脸颊推圆
  （这是它训练数据里的强关联）。所以"表情"与"脸型比例"在模型里**不是正交的**。
- 有效动作（结构性解法，不是加形容词）：
  ① 首选——**换一个不触发夸张的表情**：把"张嘴大笑"改成"**闭嘴微笑、嘴角露出虎牙**"
     （仍满足设定里的"小虎牙"，但不再触发夸张）；
  ② 次选——保留张嘴，但把解耦写死：`嘴张开露齿，但眼睛保持与其它格相同的细长半阖形状，
     不要因为张嘴就把眼睛画大`，并重申眼型的相对量锚点（眼高约脸高五分之一、横向偏长）。
- 推广成一条可复用的判断：**凡"像不像某个具体角色"很敏感的活，表情要挑"不触发夸张"的那些**；
  大笑、大叫、惊讶这类会让五官比例整体漂移。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 参考图里"像是靠运气"的构图效果，拆成"谁越过哪条线"就能复现

- 现象：用户想要参考图2 那种"中间人物跳出框架"的视觉效果（她腿脚越过页框下缘、框线在腿处断开）。
  听起来像是一种"感觉"，很难用词描述。
- 根因（可复用的认识）：这类效果**不是氛围，而是三条可写死的几何关系**——
  ① **谁**越过（中间那一格的全身）；② **越过哪条线**（外框的下缘线，不是左右或上边）；
  ③ **线在那里怎么了**（线在腿经过处断开、被腿遮住，因此下缘线不完整）。
  再加一条辅助条件：让越界的那一格**明显大于其它格**，否则"越界"读不出来。
- 有效动作：按上面四条逐条写进提示词，并补负向
  `不要让外框下缘线完整地横在她腿前面 / 不要把脚关在框内 / 不要在框线处把腿切断 / 但也不要让左右两格越出框外`。
  一次即成。
- 一句话推广：**凡"跳脱、破格、穿插"这类感觉型要求，都先把它翻译成"谁与哪条边界发生关系、边界因此变成什么样"。**
- 可复用？：是 → 已写入本节

## 2026-09-19 · 多视图页里，"相似"与"像同一个人"的差别该放在哪一层

- 现象：用户对同一页三视图先抱怨"中间那格不像同一个人"（太不像），后又抱怨"三格发型配饰过于相近"（太像）。
  两次抱怨方向相反，但都是同一个原因——**没有区分"哪些该一致、哪些该变化"**。
- 根因：多视图页的"活"来自**可变的造型状态**，而不是"把脸画成三张不同的脸"。
  在**脸的形状与角色特征**上求变化 → 变成三个人；在**束法／佩戴／角度／表情／视线**上求变化 → 才是设定稿的读法。
- 有效动作（可直接复用的两层清单）：
  - **必须一致**：脸型五官、发长与发色、服装款式与主体配件（黑领结／荷叶边／挂件）。
  - **必须不同**：马尾的束法与走向、头饰的**佩戴状态**（全戴／只戴一部分／拉到别处／被头发遮住）、
    表情、视线方向、身体角度、镜头尺度。
- 附带一条更贴设定的做法：**场景性配件不该每格都戴齐**——本例里"云朵饰带＋发夹＋向日葵"是那一场戏的配件，
  用户给的其它官方图里她只有太阳镜或一朵小花。让佩戴状态逐格不同，既拉开差异又更符合原作。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 角色有原作设定时，先去查设定再改比例

- 现象：用户抱怨"太过于幼态"，我一开始判断"要往清秀成熟的年轻女性走、把幼态特征压掉"。
  查了资料才发现**方向错了**：设定里明写她"脸颊有些婴儿肥""嘴角还有小虎牙""可爱软萌、古灵精怪"，

  判定标准：**该特征是"设定指定的"还是"模型默认的"**——前者保留，后者才收。
- 可复用？：是 → 已写入本节

## 2026-09-19 · 我把输入裁掉的那一块，正是模型会自己乱编的那一块（服装不稳定的真因）

- 现象：连续四版，角色下半身的服装每次都不一样——背带＋短裤 → 白裙 → 衬衫长裤 → 白短裤。
  我一直在负向里加"不要新增裤装／裙装／外套"，毫无作用。

## 2026-09-22 · 正向"视觉蒙版"在实际接口上产不出局部编辑（6 次调用被逐个排除变量；**当天下半场已找到解法，见下条"解药"**）

- 现象：`run_round.py --mask <png>`（蒙版＝涂红的那块**要改**）连续 6 次调用，
  要求把涂红区画成一个**纯黑色的实心蝴蝶结**，**一次都没有出现**：
  蒙版内改动均值只有 **2.1–2.5**（纯黑物体应带来约 200 的落差），改动 >30 的像素仅占 **0.09%–0.23%**。
  最硬的一条证据：四次输出的**彼此平均差只有 0.024–0.034**（等于同一张图的重编码噪声）——
  即**每次都在交回同一张近原图**，与提示词、质量档都无关。
- 变量逐个排除（每次只动一个）：
  ① 提示词三套——"强约束版"、"只留正向的极简版"、"明确写**不要复原原内容**的版本" → 全都不动；
  ② `--quality low → high` → 不动；
  ③ 蒙版位置（空白天空 → 头发）→ 不动。
- 根因（判断）：涂红是"标记"这件事对模型的信号太强——它把任务读成"**把标记去掉、恢复原样**"，
  于是把涂红区**复原成原内容**，而不是换成提示词要求的新物体。所以正向通道实际上退化成"原图返回"。
- 反面：**反向 `--mask-invert` 的保护是真的**。唯一一次让模型真的重画全图的测试（整体改黄昏雪景）里：
  可改区 86.6% 像素改动 >30、均值 53.94；保护区**中位 0.00**、核心区 **54.3% 像素逐像素完全相同**。
- ⚠ 但反向保护有一条硬代价：**保护区是原像素硬贴**。整体换色时，保护区会在新画面上留下一块
  **硬边色块**（实测对照图 `round_snow/work/_zoom_mask_face.png` 里那块冷调圆盘）。
  → **反向蒙版不能用来做整体调色**，只能用"这一块必须逐像素不变"的场合。
- 工程副作用（实测）：蒙版路径要发**两张全尺寸图**（`image` + 涂红的 `image[1]`，各约 1.06–1.09 MiB），
  且**不走压缩梯子** → **1536×1024 = 2.15 MiB 被 HTTP 400 拒**，2048×1152 = 2.70 MiB 同样必拒；
  只有 1024×1024（1.65 MiB）能过。`mask` 字段本身只占 **8.5 KB**（原以为它是浪费，实测推翻）。
  已加硬门禁：超 1.96 MiB **直接拒发**并在发送前把涂红图落盘供人确认位置。
- 可复用？：是 → 已写入 `SKILL.md` 升级规则第 1 条、`references/pipeline-notes.md` 第十节、
  `round_lib/run_round.py`（门禁 + 涂红图落盘）
- ⚠ **本条的"没用"只对"不加 `--mask-primary` 的用法"成立**——解法见下面同日的「正向局部改图的解药」。
