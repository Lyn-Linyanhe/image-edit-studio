# 接口约束 · 脚本口径 · 已实测结论

## 一、接口分两类，约束不同

### Edits 类（本项目实际使用的那条）

- **没有 denoise 参数**，改动力度无法直接控制；想动得多要靠提示词与投喂图，不是靠参数。
- **没有独立负向通道**：负向只能用正文那一段替代。所以负向必须写成完整、可解析的短语串，且要与正向明确分隔。
- **没有 mask 字段**：做不了"只重绘这一小块"。历史管线里只有一个 `--protect`（矩形保护区，其余可改），语义与"局部重绘"相反。
  → 需要局部重绘时，只能把区域裁出来单独生成再贴回，或者回到"改投喂图 + 全图重跑"。
- **上传顺序要在正文里点名**（图1／图2／图3…），并声明每张承担什么角色。
- **尺寸跟随目标图**；但见下面第三条"尺寸不受控"。


## 二、像素级色相兜底的前提

做法：在 Lab 里用**生成图的 L** ＋ **目标图的 h / C** 重组。

**前提**：生成图与原图几何位移要小。位移大时色相会错位、糊到别处，此时不适用——验收改人工比对。
**另**：做兜底前必须先统一分辨率（见下）。

## 三、尺寸不受控（已实测）

历史上出现过：请求 `1024x1024`，接口实际返回 `1254x1254`。
同时目标图可能是另一个尺寸（例如 `1200x1200`）。

**后果**：直接做像素级色相兜底、或把原图上的文字贴回，都会因分辨率差而错位。
**动作**：兜底或贴回之前，先重采样到同一尺寸；比较两组统计时也要用同一尺寸。

## 四、量测脚本的口径陷阱（必读）

以本项目 `analyze_style.py` 为例，实际口径如下（读源码确认，不是猜的）：

| 指标 | 口径 | 陷阱 |
|---|---|---|
| `paper_white_ratio` / `content_ratio` | 三通道**同时 > 0.94** 记为纸白 | 底白带颗粒时会把底白判成内容；底白偏暖时漏判 |
| `sat_mean_content` / `sat_p90_content` | 内容区饱和度均值与 90 分位 | 两者之差才能区分"整体低饱和 + 少量高饱和点缀"与"全局均匀中高饱和" |
| `val_mean_content` / `val_std_content` | 内容区明度均值与标准差 | 同时被"有没有场景背景"与"有没有装饰符号"拉动，单独作验收线风险高 |
| `lum_p05` / `lum_p95` / `contrast_range` | 全图分位与跨度 | 用来看有无死黑与整体跨度 |
| `ink_line_color` / `ink_lum` | **每图**内容区最暗 2% 像素均色 | **相对量**：整幅偏暗的图会把暗部当成墨线，组内方差被内容主导 |
| `wash_ratio` | 内容区中 S < 0.12 的占比 | 把"近白留白"与"淡低饱和着色"混在一起，且与 `paper_white_ratio` 重叠 |
| `edge_density` | 全图亮度边缘密度 | 会被"有没有场景背景"直接改变方向，不是纯风格量 |
| `hue_family` / `palette_top10` | 色相族占比与调色板 | 纯配色量，按 R1 只可用于证伪，不可入验收线 |
| 缩放 | `load_image` 把长边缩到 **900** | 跨组比较必须同缩放，否则 `edge_density` 不可比 |

## 五、目录分置铁律（已实测）

**参考组、同角色异风格对照、异风格参照、输出图，四者必须分目录。**
多放一张，聚合值整体偏掉——历史实测：某目录里除目标图外多放了一张预览图，明度从 0.496 变 0.592、P05 从 0.291 变 0.399。

建议结构：

```
<风格名>/
  input/        原始输入（只读，不改）
  work/         预处理产物（擦除后的内容图、蒙版、可视化）
  out/          rNN.png
  runs/rNN/     该轮提示词、参数、耗时、体检结果
  *_stats.json  各组量测结果
```

## 六、证伪要三层（缺一层验收线不成立）

1. **参考组自身区间**
2. **同角色异风格对照**——剥离"内容混杂"的唯一手段。当参考组是同一角色的同一批图时，它的"共同手法"里混着同一生成配置的产物，只用异风格对照剥不干净。
3. **异风格参照组**——单独目录，单独跑。

凡参考组与任一对照组数值接近的指标，一律作废；未通过证伪的不得写进验收线。

## 七、多图请求的体积上限（已实测 2026-09-19）

- 现象：两张图合计 **2.12 MB** 时接口返回 `400 {"message":"form field too large or incomplete"}`；**1.68 MB 通过**。
- 关键坑：`normalise_to_size` 在发送前会把**每一张**统一缩放到目标尺寸（如 1024×1024）再编码成 PNG。
  所以**按源图分辨率压缩完全没用**——两次源图分辨率差一倍的上传，发送字节几乎一模一样
  （2,222,178 → 2,225,769）。真正决定体积的是**画面内容的高频细节**。
- 有效杠杆（按收益排序）：
  1. **裁掉与本次迁移无关的画面区域**——本例把带场景的姿态图裁到只含人物与桌面，
     1.03 MB → 0.81 MB；顺带减少场景泄漏，一举两得。
  2. **调色板量化**——多为平涂的插画 256 色 → 128 色，1.09 MB → 0.84 MB，肉眼几乎无差。
  3. **0.5–0.8 px 的极轻微高斯模糊**——压掉抗锯齿产生的高频噪声，0.80 → 0.74 MB。
- 经验目标：**两张合计 ≤ 1.6 MB** 比较稳。

## 八、结果下载会断连，且原脚本不重试（已实测 2026-09-19）

- 现象：HTTP 200 之后，脚本去取响应里的 `url` 时抛
  `http.client.RemoteDisconnected: Remote end closed connection without response`，
  **已经计费、已经生成好的图直接丢失**（原实现在该处没有任何重试）。
- 对策：用带退避重试的包装器（本项目里是 `style-distill/round_lib/gen2.py`，复用 `gen.py` 的 payload 构造，
  只把下载换成重试），并且**在拿到 URL 的瞬间就打印出来**，这样即使下载失败也能手工取回。
- 一般原则：凡"生成一次就计费"的接口，**下载路径必须有重试**，且中间产物（URL／id）要先落日志再消费。
- **重试参数的选择（2026-09-19 第二次实测后修正）**：第一次实现用了"300 秒超时 × 5 次"，
  结果下载一挂就把整条命令拖死（生成早完成了，图反而没拿到）。
  正确的是 **短超时 + 多次**：**30–60 秒超时 × 5 次**，实测第一次尝试即成功。
  判据：下载超时应当明显短于生成耗时，否则一次挂起就会吃掉后续所有重试的预算。
- 只要 URL 已经打印出来，**即使脚本被杀也能手工取回**——这是"先打印再消费"的价值所在。
- **下载用 curl，不要用 urllib（2026-09-19 实测）**：同一个 URL，`urllib.request.urlopen(timeout=45)`
  出现"连第一次尝试都不返回、整条命令被杀且无任何输出"；换成
  `curl.exe -sS -L --max-time 60 --retry 3 --retry-delay 3 -A "curl/8.0" -o <out> <url>`
  **一次成功**。该 CDN 上 Python 的连接停滞不在 socket timeout 涵盖范围内（疑似 TLS 阶段挂住）。
  域名解析与 443 连通性都正常——所以这类挂死**只有换工具才看得出来**。
  生成脚本里建议直接 `subprocess.run(["curl.exe", ...])`。

## 九、长耗时请求怎么跑（已实测 2026-09-19）

- 管线里 `call()` 的请求超时是 **900 秒**。
- **命令超时必须大于请求超时**，否则进程会在合法等待中被强杀：实测把命令上限设成 600 秒时，请求跑到 600 秒被杀，`out_r3.png` 没生成。
- **必须加 `python -u`**：不加时 stdout 被缓冲，进程一死输出全丢——连"发送了多少字节"都看不到，无法判断卡在哪一步。
- 推荐姿势：**后台任务 + `-u`**，然后轮询读取；失败时先看已输出的日志再决定重跑。

```powershell
# 后台起，之后轮询 job 输出
python -u <script> <args>     # run_in_background = true
```

- 正常耗时参考：单张 `1024x1024 / quality=low` 约 **45–90 秒**；明显超出这个区间（例如 >300 秒）要当作"对端异常"处理，而不是继续等。

## 十、蒙版（视觉蒙版）什么时候该用、什么时候有害（2026-09-19）

这条接口的蒙版不是常规 mask：
- `mask` 表单字段**被静默忽略**（实测 0% 生效）；
- 真正起作用的是把**要改的区域硬涂成纯红**，合成成一张图随 `image[1]` 送过去；
- 历史结论："改区域 100% 生效、保护区完全不动"。

⚠ **2026-09-22 复测修正**（证据见 `../../验收_局部改图与工具链_2026-09-22.md`）：
用 CLI 路径（`run_round.py --mask`）实跑 **6 次正向蒙版，一次都没有产生要求的编辑**：
蒙版内改动均值仅 **2.1–2.5**（要求画"纯黑蝴蝶结"应出现约 200 的落差），改动 >30 的像素只占
**0.09%–0.23%**；四次输出的**彼此平均差只有 0.024–0.034**（等于同一张图的重编码噪声）。
换提示词（含只留正向的极简版、以及明确"不要复原原内容"的版本）、换 `--quality high`、
换蒙版位置（空白天空／头发）**全都不变**。
→ 结论：**"改区域 100% 生效"这半句在正向用法上不成立**——模型把涂红区**复原**成了原内容，
而不是换成提示词要求的新物体。
→ **反向 `--mask-invert` 的保护是实测有效的**（唯一一次让模型真的重画全图）：
可改区 86.6% 像素改动 >30、均值 53.94；保护区**中位 0.00**、核心区 **54.3% 像素逐像素完全相同**。
→ **体积门禁**：蒙版路径要发**两张全尺寸图**（`image` + 涂红的 `image[1]`，各约 1.06–1.09 MiB），
所以体积≈单图两倍且**不走压缩梯子**：实测 **1536×1024 = 2.15 MiB → HTTP 400**，
2048×1152 = 2.70 MiB 同样必拒；只有 1024×1024（1.65 MiB）通过。`mask` 字段本身只占 8.5 KB（去掉没用）。

**代价**：`vis = vis*(1-m) + red*m` 是硬覆盖，**可改区域的原有信息被整块抹掉**（明暗、网点、颜色全没了），
模型只能靠提示词与其它参考图去重建。

**判据（一句话，已按 2026-09-22 实测修订）**：要改的区域是否"**本来就要把内容清掉**"？
- **是**（换背景、抹掉某物、重画一整块）→ 语义上蒙版最合适，但**正向通道实测产不出编辑**，
  实际要改走"整图 + 硬约束提示词"或**投喂前物理擦除**（R5）。蒙版目前**只有反向保护这半可用**。
- **否**，且必须保留结构（上色、只补细节、只改明度）→ **蒙版有害**，应改走"整图 + 硬约束提示词"。
- 走反向保护时记住：**保护区是原像素硬贴**，整体换色会在新画面上留下一块**硬边色块**
  （实测对照图 `round_snow/work/_zoom_mask_face.png` 里那块冷调圆盘），
  所以**反向蒙版不能用来做整体调色**，只能用于"这一块必须逐像素不变"的场合。

工程入口：`mask_edit_app.make_visual_mask(image, canvas_mask, tw, th, pad, invert)`，
其中 `canvas_mask` 是 RGBA、**alpha=255 表示"要改"**；返回值 `(vis_png_bytes, pad_paint)`。
配套 `build_mask_alpha(pad_paint)` 生成 OpenAI 约定的 alpha 蒙版（本中转站不认，但发送无害）。
`gen.py --mode mask --protect x0,y0,x1,y1` 是它的单矩形简化版（**保护矩形内、其余可改**，与"只改一小块"相反）。

CLI 侧要做任意形状的局部改图，需要自己按上面的约定生成 RGBA 画布蒙版再复用这几个函数——
`gen.py` 的 `--protect` 单个矩形表达不了任意形状。
